3부 · 스킬 제대로 만들기 · 11차시

스킬 호출과 라우팅

호출은 먼저 '써도 되나'(권한)를 보고, 그다음 '맞나'(관련도)를 본다. 둘을 섞으면 조용히 실패한다.

핵심 정리

스킬이 시작되는 5가지 길

  1. 사람이 이름을 불러서 (예: /release-readiness v2.4.0)
  2. 모델이 알아서 골라서
  3. 앱이 정해진 흐름에서 켜서
  4. 다른 스킬이 요청해서
  5. 평가 도구가 시험하려고

권한 2×2

사람 호출모델 선택모드예
가능가능공유코드 설명, 테스트
가능불가사람 전용배포, 결제 내보내기
불가가능모델 전용내부 안내, 지원 절차
불가불가앱 전용·꺼짐단계적 출시, 미리 불러오기

user-invocable: false는 사람의 직접 호출만 막고 모델 선택은 막지 않는다. 필드 이름은 프로그램마다 뜻이 다르고, 모르는 프로그램은 무시할 수도 있다.

좋은 설명의 4요소

  1. 할 수 있는 일
  2. 내놓는 결과
  3. 써야 할 때
  4. 쓰지 말아야 할 때

"릴리스를 도와줍니다" 같은 설명은 엉뚱한 요청에도 끼어든다. 키워드를 잔뜩 늘어놓는 것도 나쁘다.

자동 선택 순서

  1. 권한으로 걸러낸다
  2. 남은 것만 점수 매긴다
  3. 기준 넘는 최고점을 고른다
  4. 없으면 고르지 않는다

전부 점수 매긴 뒤 1등이 권한이 없어 거절되면, 쓸 수 있던 2등까지 막힌다. 그래서 거르기가 먼저다.

기록할 5단계

허용됨 → 선택됨 → 활성화됨 → 실행 중 → 완료 확인. "스킬 사용함: 예" 한 줄로는 어디서 실패했는지 알 수 없다.

코드가 하는 일

  • 호출 주체(사람, 모델, 에이전트, 앱, 스킬, 평가 도구)와 권한 정책을 나눠 모델링한다.
  • 공통 규칙 어댑터와 확장 필드 어댑터를 따로 둔다.
  • 권한 표를 만들어 보여 주고, 요청마다 "허용 거르기 → 점수 → 선택 또는 기권" 결정을 이유와 함께 돌려준다.
  • 모델 API 없이 6가지 경로를 정해진 대로 돌려 권한 경계를 눈으로 확인한다.

스킬끼리 부를 땐 대상, 할 일, 입력 경로, 기대 결과, 이유, 실패 시 대안, 최대 깊이를 적어 보낸다. 대화 전체를 통째로 붙이지 않는다.

선생님께 적용

설명 시험 — 스킬마다 "쓰면 안 되는데 단어가 겹치는 요청"(근접 사례)을 10개 만들어 보면 설명의 약점이 드러난다. 예: 자막 PPT 스킬에 "설교 요약해줘"가 들어와도 켜지면 안 된다.

중단 대비 — 긴 작업 스킬은 중간 결과를 파일로 남겨, 끊겨도 그 파일에서 다시 시작하게 쓴다. 보이지 않는 대화 기억에 기대지 않는다.

직접 해볼 것

아래 스킬 description을 보고 테스트 요청을 만들어줘. - 켜져야 하는 요청 5개 (말투를 바꾼 것 포함) - 켜지면 안 되는데 단어가 겹치는 요청 5개 - 완전히 무관한 요청 3개 그리고 지금 description으로 헷갈릴 만한 요청을 짚고, 할 수 있는 일/결과/써야 할 때/쓰지 말 때 4요소를 넣은 새 description을 제안해줘. [description 붙여넣기]
