3부 · 스킬 제대로 만들기 · 9차시

Agent Skills 계약과 실행 경계

스킬은 SKILL.md 하나가 아니라 폴더 전체다. 발견됐다고 켜진 게 아니고, 켜졌다고 허락받은 게 아니다.

핵심 정리

스킬이 다른 것과 다른 점

도구답하는 질문
프롬프트이번 한 번만
저장소 지침이 폴더 안에서의 규칙
도구(MCP 등)어떤 기능이 있나
스킬이 일을 어떤 순서와 판단으로 하나 (여러 상황에서 재사용)

SKILL.md 계약

  • 필수 앞머리 — name(폴더 이름과 같게), description(무엇을 하고 언제 쓰는지, 라우팅에 쓰임).
  • 선택 앞머리 — license, compatibility, metadata, allowed-tools.
  • 본문 — 작업 순서, 판단 지점, 실패했을 때 행동.
  • 특정 프로그램 전용 필드(disable-model-invocation, model, hooks 등)는 다른 곳에서 안 통할 수 있다. 어댑터로 보고 대안을 적어 둔다.

스킬의 8단계 생애

  1. 발견 (패키지 찾기)
  2. 검증 (잘못된 패키지 거르기)
  3. 목록화 (이름과 설명 공개)
  4. 선택 (관련 있는지 판단)
  5. 활성화 (본문을 창에 넣기)
  6. 공개 (참고 파일을 필요할 때 읽기)
  7. 실행 (허락된 도구로 작업)
  8. 확인 (결과를 따로 점검)

단계를 뭉개면 헷갈린다. 스킬이 도구 이름을 적어도 그 도구가 생기지 않는다. 도구는 실행 프로그램이 가지고 있다. 스킬끼리는 서로 import하지 않고, 필요하면 "이 단계에서 저 스킬 결과를 쓰고, 없으면 이렇게"처럼 흐름으로 잇는다.

코드가 하는 일

  1. parse_frontmatter — 앞머리와 본문을 나눈다.
  2. validate_skill_text — 필수 칸, 이름 규칙, 모르는 확장 필드, 본문 유무, 길이 제한을 검사하고 문제 코드를 돌려준다 (참/거짓 하나가 아니라).
  3. select_primitives — 일의 모양으로 도구를 고른다. 재사용 판단 → 스킬, 사건 반응 → 훅, 외부 기능 → 도구, 분리된 맥락 → 서브에이전트, 지역 규칙 → 저장소 지침, 한 번 → 프롬프트.

검사 순서도 중요하다. 구조 문제를 먼저 보고 내용 규칙을 나중에 봐야 원래 원인이 가려지지 않는다.

선생님께 적용

스킬 정리 — 설교 자막, 프롬프터, 워크북처럼 만든 스킬마다 "이건 정말 스킬인가, 한 번짜리 프롬프트나 프로젝트 지침이 맞는가"를 먼저 분류해 본다. 모든 반복 지시가 스킬일 필요는 없다.

본문 점검 — 스킬 본문 문장을 라우팅·절차·정책·참고·출력 계약으로 표시해 보면 섞인 부분이 보인다. 참고 자료는 references 폴더로, 출력 형식은 따로 모은다.

직접 해볼 것

  1. 스킬 하나의 SKILL.md를 붙여 넣고 아래로 검토받는다.
아래 SKILL.md를 검토해줘. 1) name이 폴더 이름 규칙(소문자, 하이픈)에 맞는지 2) description에 '무엇을 하는지'와 '언제 쓰는지/언제 안 쓰는지'가 다 있는지 3) 본문 문장을 라우팅/절차/정책/참고/출력 계약으로 분류하고, 자리가 잘못된 문장을 표시 4) 특정 프로그램에서만 통하는 필드가 있는지 결과는 표로. [SKILL.md 붙여넣기]
