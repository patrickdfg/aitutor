3부 · 스킬 제대로 만들기 · 13차시

스킬 평가, 패키징, 이식성

"데모 한 번 됐다"는 여섯 가지 실패를 가린다. 스킬은 검사·라우팅·효과·안전·설치·이식을 각각 통과해야 끝난다.

핵심 정리

코드보다 먼저, 일을 뽑아낸다 (10가지 질문)

무엇이 시작시키나 · 무엇은 시작시키면 안 되나 · 어떤 근거부터 보나 · 판단이 필요한 곳은 · 자동화할 단계는 · 지켜야 할 규칙은 · 범위 밖은 · 완료를 증명하는 결과물은 · 검토자는 어떻게 확인하나 · 특정 환경에 기대는 단계는.

판단(분류, 종합, 모호함)은 모델에, 정해진 계산(해석, 검사, 세기)은 스크립트에 둔다.

작성 순서

결과물 계약 → 검증 방법 → 근거 수집 도구 → 판단 지도 → 참고 파일 → 본문 → 설명 → 프로그램별 어댑터 → 평가 → 설치 시험.

출시 6단계

단계확인
1. 패키지 구조앞머리, 참고 경로, 크기 제한, 비밀 패턴, 출력 계약 섹션
2. 라우팅양성·바꿔 말한 양성·음성·근접 사례·경쟁 스킬·적대적 문구로 정밀도·재현율. 실제 프로그램에서 시험해야 한다
3. 효과스킬 없음 vs 있음을 같은 조건으로 비교. 정확성, 완결성, 효율, 근거, 범위, 회복, 사람 수고
4. 스크립트빈 입력, 깨진 입력, 반복 실행, 시간 초과, 미리보기 등 단위 시험
5. 안전범위 밖 요청, 악성 참고 입력, 경로 탈출, 네트워크, 인증 노출, 파괴 행동
6. 설치·이식깨끗한 곳에 설치한 사본을 검사. 해시 목록, 프로그램별 지원/조정/축소/미지원 표
  • 한 단계 통과가 다른 단계를 대신하지 못한다. 글이 잘 써졌다고 권한 위반이 상쇄되면 안 된다.
  • 여러 번 돌려야 편차가 보인다. 70% 성공은 한 가지 실패일 수도, 여러 실패일 수도 있다. 평균이 올라도 과제별 퇴보는 보고한다.
  • "이식 가능"은 참/거짓이 아니다. 어떤 동작이 어디서 되는지 표로 적는다. 조용히 기능이 빠지는 것이 가장 나쁜 이식 버그다.

코드가 하는 일

출시 검사기다. 패키지 정적 검사, 라우팅 사례와 반복 실행 결과로 정밀도·재현율 계산, 결과물 계약 검사, 스크립트·안전 근거 검사, 해시 목록 생성과 설치본 확인, 프로그램별 기능 표를 만든 뒤 단계별 판정을 JSON으로 낸다. 외부 인증이 없으면 "시험용 통과"와 "실서비스 준비"를 구분해서 후자는 거짓으로 둔다.

선생님께 적용

평가 세트 — 자주 쓰는 스킬마다 켜져야 할 요청 10, 무관한 요청 10, 헷갈리는 요청 10을 파일로 모아 두면 설명을 고칠 때마다 다시 확인할 수 있다. 설명을 고치기 전에 사례부터 만든다.

효과 확인 — 같은 원고로 스킬 없이 한 번, 스킬로 한 번 만들어 비교해 보면 스킬이 실제로 무엇을 개선하는지 보인다. 렌더 확인 결과를 근거로 남기는 선생님 방식이 3단계 평가에 해당한다.

이식 — 같은 스킬을 Claude 앱과 Claude Code에서 써 보고 되는 것·안 되는 것을 표로 적어 둔다.

직접 해볼 것

아래 스킬의 출시 점검을 해줘. 1) 결과물 계약: 완료를 증명하는 결과물과 확인 방법이 본문에 있는지 2) 라우팅 사례: 켜져야 할 요청 10, 무관 10, 헷갈리는 요청 10을 만들어 표로 3) 스크립트: 빈 입력·깨진 입력·반복 실행 때 어떻게 되는지 본문에 있는지 4) 안전: 원본 덮어쓰기, 외부 전송, 삭제가 있는지 단계별로 통과/보완 필요를 표시해줘. [SKILL.md 붙여넣기]
